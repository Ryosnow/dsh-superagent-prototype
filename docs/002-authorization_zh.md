# 002 授权

授权决定谁可以开工，以及那件工作可以包含什么。这份文档建立在 [001 领域模型](001-domain_zh.md) 之上。

宿主强制执行允许名单、规则和授权。消息、评论和被引用的文档是一次决定的输入；它们改不了那些权限。

## 一条触发的两条路

### 评估：决定要不要开工

来源记下一条消息是否对着智能体：`mention` 表示提及了机器人或智能体账号，`direct` 表示一条私信。准入检查发送者和来源的策略：

- 允许名单上的人对着智能体说，构成一次明确请求。
- 人在一条已有工单的线程上的后续，遵循下面的规则。
- 其他人的消息，使用它们接收范围的准入表。
- 来源机器人名单上的机器人可以产生一个推断候选，绝不会产生明确请求。其他机器人不准入。

### 订阅：继续已有的工作

已订阅线程上的每条消息都作为上下文到达已订阅的工单，包括来自机器人和持续集成的消息。这次送达绕过准入，不授予新的权威。每张工单仍受它的授权限制。

人在一张工单自己的线程上的消息，属于那张工单的执行器来决定。主 Session 把一条消息附到一张工单上时也一样。执行器持有这条消息期间，它不做评估，也没有决定。每个执行器要么在自己工单的范围内处理请求，要么把它交还，以便路由到别处。

持有在工单活着的时候继续，即使有人去掉了它的订阅。它也覆盖一张没有被人停掉、并且有消息等着恢复它的已结束工单。

主 Session 收到一条后续通知。执行器持有这条消息期间，主 Session 只能应人的请求停止工作；接受、附上、忽略和重新排队都被拒绝。一次停止仍要过准入，强度是下面说的后续强度。

### 交还并放开后续

执行器在消息要求的工作超出工单范围、或属于另一张工单时，把消息交还一次。工单保留它的订阅。若一条附上的线程无关，执行器把在那里持有的消息交还。

一条消息只有在不再有工单持有它之后，才进入一次全新的评估。它的候选包含执行器的理由。准入把它当作那条线程上的一条普通消息来判断，主 Session 可以接受它、把它附到别处，或忽略它。交还一张工单并未持有的消息，例如一条机器人消息，或一条人已经送去评估的消息，什么都不排队。

一张工单结束时，放开它的执行器没有读过、也没有接过的后续。这包括从未送到执行器的消息，以及在它最后一次报告或一轮结束之后才送到的消息，前提是它既没有确认收到、没有回答，也没有交还。每条被放开的消息，在没有其他工单持有它时进入评估。一次停止只结束被停掉的那张工单的工作。

一张被停掉的工单不会把它的停止消息再送去评估，除非另一张工单把它交还了。停掉它的主 Session 可以把这条消息的其余部分作为新工作接受。

人可以从面板把一条被持有的后续送去评估。若主 Session 随后把它附回一张活工单，执行器会再次收到它。当没有任何有效判断覆盖这条消息时，面板也提供重新评估。

### 仅作上下文的订阅

执行器可以跟随一条相关线程，例如另一个议题或拉取请求，用来作上下文。它的消息到达工单，但不授予权威或后续强度。那里的人的消息不恢复一张已结束的工单，除非主 Session 附上了来自那条线程的一条消息。主 Session 关于其他工作的说明也只是上下文。

到达不了任何工单的人的消息，包括工单被人停掉的线程，走评估那条路。机器人消息独立于它们向已订阅工单的送达，也走那条路。

## 强度

| 强度 | 情形 |
| --- | --- |
| 明确 | 名单上的人对着智能体说，或在一条已有工单的线程上后续；准入表的一格设成明确请求 |
| 推断 | 不在名单上的人在一条有工单的线程上后续，除非他们那一格准入是明确；准入表的一格设成推断候选；来源机器人名单上的机器人的消息，对着智能体说，或出现在来源接收每条消息的地方 |
| 不准入 | 任何其他机器人的消息、准入表忽略的一切，以及接单模式为 `off` 时的每一个推断情形 |

对不在名单上的人，明确的准入格优先，即使在有工单的线程上也如此，并且在每种接单模式下都生效。否则他们的后续是推断的，在 `off` 模式下不准入。只为上下文而跟随的线程上的消息，使用准入表，而不用后续强度。

## 准入

每个来源的策略有一张准入表。它的行是接收范围：

- **飞书：** 每个已配置的群、机器人会收到提及的其他群，以及私信。其他群只有在飞书卡片上把 **其他群** 设成 **仅 @** 时才接收。
- **GitHub：** 新议题、新拉取请求、评论，以及默认分支的持续集成。

一行最多三格。每一格决定一条消息成为明确请求、推断候选，还是什么都不是：

| 格 | 选项 | 默认 |
| --- | --- | --- |
| 在名单上，没有对着智能体 | 推断、忽略 | 推断 |
| 不在名单上，对着智能体 | 明确、推断、忽略 | 忽略 |
| 不在名单上，没有对着智能体 | 推断、忽略 | 忽略 |

未对智能体说话的消息的那些格，只在来源接收每条消息的地方可用，例如一个飞书群设成 **全部消息**，或一个 GitHub 范围打开了接收全部的开关。一条持续集成结果没有发送者，所以它的行只提供最后一格。机器人消息用机器人名单，不用这些格。

把「不在名单上、对着智能体」那一格设成明确，就让那个范围内的任何人都能通过提及智能体来要求工作。这对一个专门的支持群可能有用。推断候选仍然取决于接单模式。后续通常绕过这张表，只有明确的那一格仍然给予明确强度。

准入表是策略版本的一部分。把一格放弱，不会立刻停掉在它之下接受的开放工单。在恢复之前重新验证时，它可以撤销它们的授权。

### 机器人与自动评审者

宿主把 GitHub 应用、以 `[bot]` 结尾的登录名，以及飞书机器人认作机器人。一个来源可以列出诸如 `dependabot[bot]` 这样的机器人，它们的消息可以成为推断候选。它们必须对着智能体说，或者发在接收每条消息的范围里。它们不能发出明确请求，也不能停止工单。

用普通账号的自动评审者，对宿主来说算一个人。它的评论到达已订阅的工单，并产生后续通知。团队的提示词必须把这样的账号标成自动评审者。

## 路由候选

主 Session 用 `orchestrator_route` 路由明确候选。一次调用可以包含若干接受、附上、停止或忽略的决定。每一项独立处理：被拒绝的一项或缺失的字段，不妨碍其他项运行。

一个推断候选通常需要一次完整研判。有一条捷径：若它的卡片明显碰不到任何启用的规则，例如普通闲聊或无关讨论，主 Session 可以直接忽略它。决定记下 `ignoredFromCard`，以便和一次规则研判区分。主 Session 在它的策略提示词段落里读启用的规则。

接受一个推断候选始终需要一次研判。直接接受会拒绝一条准入没有作为明确而放行的触发。

## 接单模式与规则

接单模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断的都不成为候选，例如一条没有对着智能体的消息、一条机器人的消息，或不在名单上的人的后续 |
| `observe`（默认） | 推断候选会被研判；肯定的研判记成忽略，并标上「本来会接受」，什么都不接受 |
| `auto` | 对一个推断候选的肯定研判会接受它 |

明确请求在每种模式下都生效。从 `observe` 开始，看过记下的决定之后再切到 `auto`。每次研判对每条启用的规则恰好判断一次，无论匹配与否。一次主动接受至少需要一条匹配的规则。

每条规则描述一种主动工作。工单的授权记下匹配到的规则，它的执行器收到它们的名字和说明。

对那张工单，一条规则的流程和沟通要求覆盖默认。一条沉默规则可以压掉确认收到；一条评审规则可以点明合并前需要的评审者和批准。适用于每张工单的要求，改放到团队提示词段落里。

## 策略版本

规则、接单模式和每个来源的策略构成策略版本。每份授权记下它被接受时所处的版本。

版本一变，就丢掉正在跑的评估，并把它们的触发重新排队。它也向每张受影响的活工单发送一条策略已变的输入。这条输入说明是哪一种：

- 一条匹配的规则变了，包括它的新文本，或者不再适用；
- 请求者可能不再能开工；或
- 主动工作不再被接受，例如因为模式从 `auto` 改掉了。

不受影响的工单收不到通知。这次变更不立刻撤销活工单的授权。

来源配置和策略是分开的。它控制什么进入系统：读哪些群，以及一个范围是接收全部消息还是只接收提及。一份授权记下它的来源和接收范围。恢复需要来源仍在听那条线程，但不要求它仍在那里接收每条消息。

来源关掉时，回复等待。来源不再听它们的目的地时，回复被丢掉。

关于执行器可以对自己的结果做什么的条件，例如何时可以合并，并不决定谁可以授权工作。它是智能体说明的一部分，不是策略的一部分。

## 恢复与停止

一张已结束的工单保留它的授权。人在它自己的某条线程上的消息可以恢复同一件工作，不需要新的评估或决定，无论是谁发的。机器人和持续集成不唤醒已结束的工单。执行器决定请求是否落在范围内，不落在范围内就结束这一轮。

只有三种操作改变一份授权：接受创建它，人的停止撤回它，重新验证失败撤销它。被人停掉的工单保持结束，不再接收任何东西。在那里要求的工作需要一次新的接受。

### 恢复前的重新验证

来源必须仍在听原来的线程。其余检查取决于授权的依据：

- 一份明确的后续授权通过。
- 一份推断的授权需要 `auto` 模式，并且它匹配的规则仍然启用。
- 由表格一格准入的授权，在今天的表和发送者成员身份下，必须仍能至少收到它原来的强度。因此把一个发送者从名单上移除，可以撤销一份经「名单上的发送者」那一格接受的授权。
- 一个机器人的授权要求那个机器人仍在来源的机器人名单上。推断的表格授权和机器人授权还需要 `auto` 模式和仍然启用的匹配规则。
- 其他授权要求发送者仍在来源的允许名单上。

重新验证失败时，工单保持结束，不取它等待中的任何消息。每条消息被当作没有到达任何工单；若没有其他工单持有它，它就进入评估。主 Session 不会被告知它到达过一个工作者。处理暂停之后也是这样。附到这张工单上会被拒绝，进一步的工作需要一次新的接受。

- **人在一条线程里说「停」是一条普通触发，** 由评估决定停止。执行器不能宣布有人要求它停。
- **面板上的停止是一条命令。** 它直接作用在工单上，并记成一次手工停止。
- **等待条件属于来源。** 「无人负责已有 N 小时」这样的条件，应当是一个会等待并自己再查的来源；评估从不等待。

## 评估没有做完的时候

时限从候选到达主 Session 时起算。等着送达的时间不算，一条没送到的候选从不过期。

一次过期的评估把它的触发排队再试一次。连续两次重试之后，第三次过期记下 `unavailable`。一次研判失败也记下 `unavailable`；后来的触发可以开始一次新的评估。策略变更，或对照一份过时策略作出的决定，记下 `unavailable`，并立刻在当前版本下把这一批重新排队。

`evals` 健康条目报告最近一小时里尚未解决的未完成决定。`scripts/dsh-superagent status` 包含那个错误。

面板只在未完成决定不到 24 小时、仍是它那条线程上的最新决定、还没有被忽略，并且线程既不在排队也不在评估中时，才要求人注意。人可以再次评估这条触发，或忽略这个问题。

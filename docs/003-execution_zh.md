# 003 执行

这份文档跟着一张已接受的工单，走过执行、交付和恢复。它建立在 [001 领域模型](001-domain_zh.md) 和 [002 授权](002-authorization_zh.md) 之上。

## 工单阶段

每张开放的工单有一个阶段，由它在等什么决定。表格从上往下读；第一行匹配的获胜。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| 人 / 送达 | 把一条输入送到执行器会话失败了；2 秒后重试，然后按翻倍的延迟，最多到一分钟，一次成功、一次新的派工或工单结束会把它清掉 | 输入未送达 |
| 人 / 回答 | 它有一项待人工决定 | 等待回答 |
| 人 / 评审 | 最新的报告是 `ready` | 等待评审 |
| 人 / 受阻、失败 | 最新的报告是 `blocked` 或 `failed`，并且此后没有人的消息到达这张工单 | 受阻 · 失败 |
| 工作中 / 排队 | 没有派工，或有一次待启动的 | 排队中 |
| 空闲 | 最新的报告是 `waiting`，或这次派工已结束 | 等待触发 |
| 工作中 | 其余一切 | 工作中 |

`person` 阶段表示这张工单没有人的输入就无法继续。一条新的人的消息把 `blocked` 或 `failed` 的工单交还给它的执行器，于是它移到下一个匹配的阶段，通常是 `working`。

一张 `idle` 的工单结束了这一轮，没有悬着的问题。已订阅线程上的一条触发可以让它继续。

## 执行器

每张工单得到一个名为 `worker-<ticket id>` 的执行器会话，以及一个以工单短名命名的目录。目录建在配置的执行根下，默认是 `<stateDir>/work`。

执行器会话以操作者的操作系统用户身份、无需批准地跑命令。它们的 `dsh-superagent-worker` 预设装着工作所需的工具，并在 5 秒后把前台外壳命令移到后台作业。这样工作者可以在下一步收到新消息，而不必等一条长命令结束。

主 Session 使用 `dsh-superagent-router`，同样是 5 秒的外壳和作业等待限制，以及一套更小的、用于路由的工具。会话保留创建时所选的预设。工作者的子智能体使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与工作者名额

一轮结束时若还有外壳作业或子智能体在跑，工单保留它的工作者名额，并保持工作中。它不会被报告成等待，主 Session 也收不到等待报告。一个完成的作业或子智能体用它的结果、在同一个名额里唤醒执行器。一轮结束且没有后台工作时，执行器照常报告等待。

每一轮之后，后台工作最多有 30 分钟来结束。到了这个限制，外壳作业被杀掉，工单被报告成等待。报告包含执行器的最后几句话，以及哪些作业被杀、哪些子智能体仍在活动。子智能体允许继续。执行器在下一轮读被杀掉的作业的结果。

向人交接会立刻释放名额，并让报告继续生效。这发生在一次 `ready` 报告或一个问题之后，除非此后又来了一条输入，也发生在任何 `blocked` 或 `failed` 报告之后。

交接时，子智能体停止。外壳作业，例如一个供评审用的服务器，可以继续到这次派工结束。它们不占名额，也不受 30 分钟限制，包括后来的轮次之后。它们完成时不唤醒执行器；执行器在下一轮读结果。

人也可以直接在执行器会话里写字，从而开始一轮。它的后台工作遵循同样的规则。

一次派工结束时，它的外壳作业被杀掉，不唤醒会话。它的子智能体被放开，它们唤醒的任何完成轮都被丢掉。接替的派工和它等待中的输入，在那次关闭完成之后才开始。

在 DeepSeek Harness 进程里停止或重启插件，走同一条关闭路径。还没进入会话历史的输入被保留。关闭最多等每个工作者的后台工作 10 秒；进程重启则直接结束那些工作。一次在忙碌中被打断的派工，带着一条恢复说明重新开始。

工作者的子智能体，包括嵌套的，使用 DeepSeek Harness 的 `standard` 预设，并带上工作者的权限。它们只保留工作者被允许的工作工具，工单结束时失去那些工具。在 `standard` 下，一条外壳命令在 60 秒后移到后台。子智能体的作业在它结束时被杀掉。

### 准备工单目录

第一次派工之前，若工单目录还不存在，准备命令在执行根里用 `sh` 跑一次。它有十分钟来结束。没有准备命令时，工作者在一个空目录里开始。

命令失败会使工单失败，并记下它的输出。一次重试，或人在工单某条线程上的一条消息，会再试一次准备。一条典型的命令用 `git worktree` 造出一份检出。一个拉取请求的分支的最后一段路径与工单短名相同时，它属于这张工单。

### 并发

一张工单从一次启动开始就占一个工作者名额，包括准备，或从唤醒它空闲执行器的那次送达开始占。它在一整轮活动期间也占着名额。

配置的并发限制用在这些名额上，另有一个额外名额给人的消息或一次状态请求。这样的唤醒在普通名额已满时可以用这个额外名额，并在一次新的启动之前取下一个空闲名额。因此新工作不能阻止人继续一张已有的工单。

其他输入，例如持续集成的结果，等待一个普通名额。一次启动在 `working / queued` 里等到有名额空出来。启动彼此并发，所以一条慢的准备命令只耽误它自己的工单。

### 执行变量

准备命令和执行器说明收到同一组执行变量。命令读环境变量；执行器在它的提示词里读它们的值和说明。没有一个含有凭证。

| 变量 | 由谁登记 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`, `DSH_SUPERAGENT_NAME`, `DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名和标识 |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源所看的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`, `DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号和它的提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`, `DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 开工单的那个议题或拉取请求，以及它是拉取请求时的头引用 |
| `DSH_SUPERAGENT_FEISHU_BOT`, `DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及开工单的那个群 |

工单专有的值来自它的目录和最初的触发。其他值来自当前的部署设置。只有面板能改执行环境的设置；发给主 Session 的文本改不了配置好的外壳命令。

工作者通过智能体账号的 `gh` 到达 GitHub，通过机器人的 `lark-cli` 到达飞书。被禁止的命令在按名字调用时失败。

这些包装和目录建立的是默认，不是一道安全边界。工作者仍然可以用绝对路径执行一个程序。

## 合并

自动合并由 **交付要求** 提示词管辖。宿主没有针对合并的专门决定逻辑。

默认情况下，执行器从不以智能体账号打开自动合并：GitHub 把合并归到打开它的那个人。交付要求必须点明另一个账号的命令行来做合并。没有的话，由人来合并拉取请求。

默认说明只允许在为这张工单打开的拉取请求上自动合并，并且它已就绪、所需的批准覆盖头提交，增加和删除合计少于 200 行。在推送另一个修订之前，执行器撤回自动合并。

没有正文的评审，例如批准，也作为触发到达，可以唤醒一个在等评审的执行器。这些说明管辖的是智能体，不是 GitHub 的合并规则。要强制批准，就在分支保护里要求它们，并忽略过时的批准。去掉合并用的命令行，或删掉自动合并那一段，就要求手工合并。

## 一张工单如何结束

- **就绪但没有拉取请求：** 一次 `ready` 报告把工单结束为已完成。
- **无事可做：** 执行器发现没有需要人行动的工作，例如一个复现不了或已被取代的请求，就报告 `dropped`。工单结束时不发消息，除非一条匹配的规则要求发一条，人后来在它的线程上的消息会恢复它。

### 拉取请求

一张工单在它的执行器报告了它起步的那个拉取请求之后，就跟随它。它也跟随从它的分支打开、并由执行器报告或由 GitHub 来源发现的每个拉取请求。重新打开的拉取请求会再次被跟随。

当它打开的拉取请求没有一个仍开放时，工单就完成了。若它一个都没打开，它所跟随的全部拉取请求都必须关闭。然后它以最近一次相关关闭的结果结束，并保留它的订阅，这样后来的人的评论可以恢复它。

一次关闭在恢复、重试或恢复中的工作还没做完时，不结束工单。若执行器确认收到或回答了它持有的一条后续，但此后还没有作出一次非进展的报告，也没有在读过那条消息之后结束一轮，它也继续等。后来的一次 `ready` 报告，在同一条拉取请求完成规则满足时结束工单。

聊天渠道收到一条关于拉取请求结果的最终通知。GitHub 已经在拉取请求自己身上显示这个结果。去掉一张工单对某个拉取请求的订阅，也让它不再跟随那个拉取请求。

因此「等待评审」的意思是一次 `ready` 报告，并且有一个拉取请求。

### 后续与上下文线程

执行器决定它的工单自己的线程上的人的后续。它处理范围内的请求，把超出范围或属于另一张工单的请求交还。一旦没有执行器持有这条消息，它就成为主 Session 的候选。除此之外，主 Session 对后续只能应人的请求去停止工作。

一条输入在会话把它带进一步、并且随后报告或结束一轮之后，算作已读。工单结束时，没有被确认收到、回答或交还的未读消息回到评估，如 [002 授权](002-authorization_zh.md) 所述。已读但没有采取行动的消息，例如一声谢谢，不回去。

只为上下文而跟随的线程仍然送达消息，但不给工单对人的后续的所有权，也不恢复已结束的工单。那些消息可以独立被研判。

来源在一张活工单订阅期间轮询已订阅的线程，并在最后一条触发与订阅工单结束这两者中较晚的那个之后，再轮询两周。此后，消息只经普通入口到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行器受阻或失败

执行器会话报告 `blocked` 或 `failed`，或启动失败或出错（这记成 `failed`）时，工单不自动取输入。

模型提供方或网络的一次过路失败，即 HTTP 408、429 或 5xx，或一次被拒绝、被重置或超时的连接，先再试，三次，退避逐渐变长：一次启动再跑，一轮失败的工作者被告知继续；失败的准备命令不再试。

一旦失败，持续集成和机器人的消息记在它上面，但不送达，也不唤醒会话。

它的工具仍然可用，所以人可以直接在会话里继续。

一次失败的启动不会自己再试。

人的一条消息、后来一次既不是 `blocked` 也不是 `failed` 的报告，或一次重试，结束这次停住。

它是从存下的报告和输入推出来的，所以重启之后还在。

### 重试

在一张开放工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：一次新的派工，重新启动它的工作者并取走等待中的输入，是每一种情况的补救。

一旦人的消息到达一张受阻或失败的工单，执行器就有了这条消息，所以工单显示为工作中，或在一次失败的启动再次开始时显示为排队，并且不再提供重试，除非送达那条消息失败了。

一次重试结束当前的派工，并在同一个执行器会话、目录、分支和拉取请求里开始一次新的。

执行器模型只在创建会话时应用；已有的会话保留它的模型。

### 重启

正在跑的派工以「宿主已重启」结束，新的派工带着一条恢复说明开始，告诉执行器在重复任何对外动作之前，先检查它的目录、git 历史和 GitHub，最老的工单优先。

处于等待、就绪、受阻或失败的派工保持原样，除非在那次报告之后有一条输入到达它们，那种情况下它们也重新开始。

会话、目录、订阅、待发消息和下面的存下的工作都熬过重启，每个执行器会话把哪些消息带进了自己的历史也熬过：一步在认领它们之后、模型调用之前做这件事。被重启切断的一轮所取走的消息，一旦随后有一次报告或一轮结束，就算已读；而一步认领了、但在进入历史之前被取消或错误切断的，算未读。

一次重试或一次重启，把被替换的那次派工已送达、但它的执行器会话没有取走的消息，再次给新的派工；取消或被切断的一步可能已经丢掉它们。一份仍在会话里等着的副本，由重启保留或在崩溃之后持久化的，会在新派工的第一条消息之前被取出，这样新的送达是唯一的副本。

### 存下的工作

dsh-superagent 在一次决定之后要做的事，例如把一个候选、一条后续或一份报告转给主 Session、启动一次派工或送达一条输入，先存下来，然后再做。

一次中转或一次送达失败时，例如它的会话联系不上，2 秒后重试，然后按翻倍的延迟，最多到一分钟；一次启动失败会使它的工单失败，除非这次失败是上面说的过路失败。

每种工作只有在一项连续失败三次之后，才在总览的系统问题里报一个错误；一次失败的输入送达改显示在它的工单上。

给主 Session 的中转保持它们的顺序，通知也是；失败的一条挡住它那种里后来的那些。

### 来源失败

GitHub 来源各自读每条议题、拉取请求和线程：一次失败的读取把错误留在它的线程上，下一次轮询再读，并计入来源的一次错误，默认连续三次失败的轮询之后报告；任何一次成功的轮询把计数清零。

GitHub 在智能体失去对一个私有仓库的访问时也回答 404，所以 404 会重试。

一条被通知到的议题或拉取请求，读取一直失败的，在第一次失败读取之后一天被丢掉，GitHub 报告它已删除时则立刻丢掉；此后它不再让轮询失败，它的线程保留错误，来源的状态点出它。

它的读取位置停在原来的地方，所以后来的通知或对它线程的一次轮询，会读到失败的读取漏掉的内容。

飞书事件消费者报告每一次失败，对已订阅话题的轮询把每次失败留在它的线程上。

GitHub 列表或飞书页面里的一条畸形项被跳过，来源的状态计数它。

### 渠道失败

发出的消息被存下，并作为存下的工作发送，从 5 秒起按退避重试，翻倍直到 300。

一张工单发到一场对话的消息，按排队的顺序出去，所以它的确认收到在后来的回答或结果之前：一条消息在同一张工单发到同一场对话的更早一条还没出去时等待，直到那一条连续失败三次并显示成一个问题。

其他工单的消息，以及不属于任何工单的消息，不等它。

一条有失败尝试的消息是一个系统问题，直到它出去或被撤回。

一条消息只有在它的来源不再听这场对话，或来源回答这场对话永远收不到它时，才被丢掉；来源关掉时，它等待。

来源对 GitHub 上已删除的议题或已锁定的对话这样回答，对飞书上已撤回的消息或飞书已找不到的消息也这样回答。

对一条已不存在的评审评论的回复，改发到拉取请求的对话里。

一条被丢掉的消息保留它的记录，包括何时、为何丢掉，以及它是为哪张工单，所以它绝不会再排队；一条被丢掉的确认收到读起来是丢掉了，不是发出了。

### 暂停处理

停止分派、新的评估、评估超时、输入送达和回复；一次已经在进行的启动等到处理恢复。

来源继续记录触发，正在跑的执行器一轮不被打断。

人发给一张已结束工单的消息等待：暂停之后的第一次通过会恢复这张工单，若它的授权在当时的策略下仍然成立。

进行中的评估在暂停期间不过期；它的截止时间按暂停的长度往后移。

### 无效配置

一份被它的种类拒绝的已存来源配置，会停用那个来源实例。

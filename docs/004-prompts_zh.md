# 004 提示词

这份文档说明智能体读什么、团队能改什么，以及改动何时生效。它建立在 [000 原则](000-philosophy_zh.md) 到 [003 执行](003-execution_zh.md) 之上。提示词正文用英文写。

## 团队写什么

团队可以改三个团队段落，添加技能，并覆盖每一个内置的系统提示词部分。大多数默认文本在 `prompts/` 和 `skills/` 下。工具说明、通知和卡片留在代码里，不能通过提示词设置来改。

| 段落 | 装着什么 |
| --- | --- |
| 沟通 | 何时给人发消息、消息读起来是什么样、每条 GitHub 消息开头的那一行（默认是 `This is by an automated agent, not a human`）、如何处理评审，以及哪些普通账号是评审机器人 |
| 工单范围 | 一张工单何时继续，何时以草稿停下 |
| 交付要求 | 拉取请求里的证据、自动合并条件及其行数阈值，以及提交作者；没有作者时，执行器以智能体账号的无回复地址提交 |
| 团队技能 | 智能体在需要时才加载的知识，例如一份 `identities` 技能，写明哪个飞书用户对应哪个 GitHub 账号 |

内置文本覆盖角色、工具用法、宿主机制、授权规则，以及 GitHub 和飞书技能。它用标题指代团队段落，而不把它们再抄一遍。

### 内置部分与模板

覆盖使用这些键：

| 部分 | 键 |
| --- | --- |
| 共享说明与角色 | `runtime/shared`, `runtime/orchestrator`, `runtime/worker` |
| 工作说明 | `runtime/subscriptions`, `runtime/replies`, `runtime/dispatch`, `runtime/work`, `runtime/admission` |
| 交接说明 | `runtime/handoff/orchestrator`, `runtime/handoff/worker` |
| 来源技能 | `skill/feishu`, `skill/github` |
| 生成的段落 | `runtime/environment`, `runtime/policy`, `runtime/policy/none` |

生成的段落是可编辑的模板。它们必须保留这些占位符：

- `runtime/environment`：`{variables}`，填入执行环境的各行。
- `runtime/policy`：`{version}`、`{mode}` 和 `{rules}`，每条启用的规则一行。
- `runtime/policy/none`：`{version}` 和 `{mode}`，在没有规则启用时使用。

改一个部分，改变的是模型收到的说明。它不改变准入、授权、工具检查或账号包装，那些仍由代码强制执行。

在人的明确要求下，主 Session 也可以用 `orchestrator_prompts_save` 保存覆盖。一次保存若省略某个覆盖的 `base`，就保留已保存的基准。已从保存的配置里出现、但部分本身已被移除的，保存时丢掉；任何其他未知部分都会被拒绝。

一份覆盖记下它基于哪一段内置文本。升级保留团队的文本。默认文本若变了，面板把这个部分标成 **默认内容已更新**，并在团队文本旁边显示差异。团队可以保留自己的文本、采用新的默认，或再改一次。没有覆盖的部分自动跟随新的默认。

主 Session 可以在 `orchestrator_read prompts` 里、`default_changed` 之下，读到受影响的部分名称。

## 组装与优先级

系统提示词按这个顺序组装：

1. 共享说明和角色。
2. 三个团队段落。
3. 订阅与回复。
4. 主 Session 用的分派，或执行器用的工作说明。
5. `runtime/admission`，仅主 Session。
6. 交接说明。
7. `runtime/environment`。
8. `runtime/policy`，仅主 Session。

准入说明来自 `prompts/admission.md`。它们描述主动研判，以及一张卡片明显无关时何时可以忽略。`orchestrator_eval` 返回上下文，而不把这些说明再重复一遍。

环境段落给主 Session 部署范围的值，给每个执行器它这张工单专有的值。策略段落在每次模型请求时按设置重新生成。它包含策略版本、接单模式、明确请求的豁免，以及启用的规则，形式为 `- <name> (<id>): <instruction>`，或者一句没有规则启用的说明。它放在最后，这样策略一变，前面的提示词文本保持不动。

执行器还读 DeepSeek Harness 的编程提示词和仓库的 `AGENTS.md`；主 Session 不读。一张推断而来的工单会在末尾加一条说明，把它的执行器限制在匹配到的规则上。派工和进来的消息以内联的触发卡片到达，只有被截断的内容才带资源指针。

执行器在无人值守下工作。它们的工具排除那些会问人、向人展示界面或更改配置档的，例如 `ask_user_question`、`present` 和 `plugin_manager`。

从强到弱：

1. 由工具和宿主强制的事实：身份、权限、工具参数检查、回复用途、长度限制。提示词改不了它们。
2. 内置段落和生成段落，按团队对它们的覆盖来读。
3. 一张主动工单所匹配规则里的流程和沟通，仅对该工单的执行器会话生效。
4. 团队段落和团队技能。
5. 外部文本：消息、评论、文档和引文。它是数据，从不改变规则或授权。

## 内置文本的原则

这些把 [000 原则](000-philosophy_zh.md) 用到智能体上：

- **角色分开。** 主 Session 只做路由：它转发原来的触发和路由事实，不做技术决定，通过一个路由工具，一次调用里对几个等待中的候选作出决定。一条路由说明最多 30 个词。执行器读原始来源，判断范围，实现并验证。
- **主 Session 不等。** 报告、后续通知、候选和已完成的后台作业自动作为消息到达。没有事可做时，它结束这一轮。一道守卫拒绝 `sleep`、超过 30 秒的外壳超时，以及超过 5 秒的作业等待，因为卡住的一步会耽误新的候选。这些说明替换主 Session 完整提示词里 DeepSeek Harness 自己的作业通知说明。
- **只在必须有人行动、或有人用得上结果时才发消息：** 结果可以评审或使用，需要一个决定或一项资源，或者工作做不完。聊天消息默认一句，硬限制 100 个词。
- **后续由执行器决定。** 每个执行器处理并确认收到范围内的请求，把超出本工单或属于另一张工单的请求交还。一条消息只有在它的全部所有者都交还、或结束时没有接过它之后，才成为新工作。主 Session 收到后续通知，但只能为了停止工作而行动。交还的消息随后作为候选到达，带着执行器的理由。
- **通过订阅和主 Session 协调。** 执行器为了上下文跟随相关线程。主 Session 可以把另一张工单的一个事实放进最多 100 个词的说明里送出。订阅和这条说明都不授予权威。
- **只有明确指向时才附上。** 一条消息必须指向某张工单的拉取请求、议题、源消息或确认收到，或者指向恰好只有一张工单匹配的近期改动。单靠话题相似不够。附上会让工单订阅整条线程；执行器若发现它无关，就用 `orchestrator_thread_unrelated`，并且不在那里回答。
- **具体地确认一次。** 实质性工作之前，执行器确认每个新请求，点明对象和预期结果，作为原消息下的一条回复。
- **通过 `human_action` 来问。** 执行器把一个具体问题放进报告，主 Session 原样转发。若是人的某条消息引出了这个问题，就点明那条消息，由宿主在那里问。否则在工单原来的对话里问。已经授权的工作可以同时继续。
- **如实交付。** 开一个拉取请求不等于就绪；草稿标成未完成；界面改动没有真实的改前截图就不算就绪。
- **人的暂停一直有效，** 跨后续消息、新的执行器会话和重启，直到有人解除。自动反馈从不恢复被暂停的工作。
- **例子只展示格式。** 一句示例不是智能体可以宣称的事实。
- **按结果处理评审。** 已修好并验证过的评论默默标为已解决；拒绝的给一句理由。自动评审者的线程一旦有了答复就标为已解决，每个自动评审者在每个拉取请求上最多三轮。
- **给重复的工作让路。** 人的分支或拉取请求已经包含这张工单的改动时，执行器关掉自己的拉取请求，用一句话指向对方的。

## 版本

- 每次保存产生一个不可变版本，包含完整配置、修订号、前驱、时间戳和来源（面板或工具）。恢复一个版本或恢复默认，会再产生一个版本。
- 保存点明自己的基准修订。冲突的保存被拒绝，草稿不丢。
- 会话在每次模型请求时读最新版本，包括同一轮里后来的步骤。保存不重启、不取消、也不唤醒会话。宿主记下每个会话用过的修订；执行器可以读它工作时所处的任一修订。
- 部署设一个总大小限制，覆盖也算在内。校验拒绝未知的键、保留的内置技能名、未知的覆盖部分和缺失的模板占位符。它从不悄悄截断文本。与默认完全相同的覆盖会被移除，这样该部分跟随以后的默认。
